# Design notes: ocaml-hexaly

This document covers the non-obvious design decisions in the binding:
the ones that took multiple iterations to get right, and the ones that
will matter if you extend it.

## 1. The four-layer stack

```
OCaml user code
   │  cheap record-wrapper indirection (1 word/handle)
   ▼
hexaly.ml / .mli              ← idiomatic OCaml
   │  external "name" declarations
   ▼
hexaly_stubs.c                ← OCaml↔C glue
   │  C function calls
   ▼
hexaly_shim_{real,mock}.cpp   ← C↔C++ bridge
   │  C++ method calls
   ▼
libhexaly14X.dylib            ← Hexaly's commercial solver
```

Why four layers and not three (skipping the shim):

- **C++ ABI is unstable** across compilers, so we can't call C++ name-mangled
  symbols directly from C. A thin `extern "C"` shim gives us a stable C ABI
  generated by the same compiler that builds Hexaly's headers.
- **C++ exceptions** can't cross into OCaml's runtime without corrupting
  the stack. The shim catches every exception (HxException, std::exception,
  ...) at the ABI boundary and routes it through a thread-local error slot.

Why two backends:

- **Real** links against `libhexaly145.dylib` and runs the actual solver.
- **Mock** is a tiny in-process brute-force solver. It's there so the
  binding compiles and the test suite runs on any CI worker (no license
  needed). The mock implements the same `extern "C"` ABI as the real
  shim. `src/config/discover.ml` writes a one-line `hexaly_shim.cpp` that includes
  one of them.

## 2. Lifetime invariant

A naive binding looks like:

```ocaml
type model     (* abstract: a raw FFI handle *)
type expr      (* abstract: a raw FFI handle *)

external get_model : optimizer -> model = "..."
```

Then a user writes:

```ocaml
let opt = Hexaly.create () in
let m   = Hexaly.model opt in
let x   = Hexaly.bool_var m in
(* ... never use [opt] again ... *)
```

OCaml's GC is free to finalize `opt` because nothing references it from
OCaml-side code. But Hexaly's `HxModel` is owned by the `HexalyOptimizer`,
so its underlying memory has been freed. The next call through `m` or `x`
is a use-after-free.

This binding fixes it by making every derived handle a record carrying
its parent:

```ocaml
type model    = { _mh : _model_h;    _mo : optimizer }
type expr     = { _eh : _expr_h;     _em : model     }
type solution = { _sh : _solution_h; _so : optimizer }
(* ... etc *)
```

OCaml's reachability analysis sees that `m._mo` points at `opt`, so `opt`
can't be GC'd while any descendant is live. Dropping the optimizer
naturally invalidates the chain.

Cost: one extra word per handle. A million expressions in a model takes
8 MB of OCaml heap (compared to 0 if the user disciplined themselves,
which they would not).

The GC-pressure test in [`test/test_hexaly.ml`](../test/test_hexaly.ml)
caught this bug originally.

## 3. The HxOperator drift problem

Hexaly's `HxOperator` enum has 65+ values in a specific declaration
order. Their integer values are determined by C++ enum semantics
(unspecified-order → declaration-order, with `O_Int` mysteriously at
position 36 instead of next to `O_Bool` and `O_Float` for backwards-compat
reasons).

The OCaml `Op.to_int` must produce the same integers Hexaly's C++
expects. Our `hxs_operator` C enum is hand-maintained to mirror
`HxOperator`.

Two layers of defense:

1. **Compile-time `static_assert`s** in `hexaly_shim_real.cpp` at every
   "sentinel" position (head, mid, out-of-order Int, tail). If a Hexaly
   minor version shuffles the enum, the build fails loudly:

   ```cpp
   static_assert((int)HXS_O_INT == (int)O_Int, "HxOperator drift: Int");
   ```

2. **`Op.to_int`** in `hexaly.ml` matches by symbolic name, with the
   integer values inlined. Update it any time `hxs_operator` changes.

This caught a real bug: my first guess at `Op.to_int` had `Sum=4, Eq=13,
If=19` etc.; the real values are `Sum=3, Eq=8, If=14`. Every model
constructed by the binding was being silently corrupted; the static_assert
fired on the first real-backend build. See git log around the initial
real-backend port.

## 4. Callbacks: the runtime lock dance

The hard part of binding any blocking C solver from OCaml is callbacks.
Two pitfalls:

### Pitfall 1: OCaml's runtime lock

OCaml's runtime is single-threaded at the bytecode level: only one thread
can be executing OCaml code at a time, gated by a per-domain mutex called
the "runtime lock". A C function called from OCaml holds the lock by
default.

If Hexaly's `solve()` (called from C, lock held) blocks for an hour, no
other OCaml thread can run during that hour. For users that's surprising.

Worse, if Hexaly spawns worker threads and invokes a callback from one
of them, that callback's trampoline needs to acquire the runtime lock
before calling back into OCaml. If we never released it, it deadlocks.

**Fix**: `caml_hxs_optimizer_solve` releases the runtime lock for the
duration of `solve()`, then re-acquires it before returning. Other OCaml
threads can run during the solve. Callback trampolines acquire the lock
before calling the OCaml closure, release it before returning.

### Pitfall 2: thread registration

In OCaml 5+, threads must be registered with the runtime to call
`caml_callback`. Hexaly's worker threads weren't created by OCaml's
threads library, so they're unregistered.

**Fix**: the trampoline calls `caml_c_thread_register()` defensively. It's
idempotent on already-registered threads, so calling it on every callback
firing is safe (just slightly redundant). We never un-register; that's a
slow bounded leak (one TLS slot per Hexaly worker thread, freed when the
process exits).

### Pitfall 3: closure liveness

The OCaml closure is allocated on the OCaml heap. If we just pass its
`value` to C and forget, OCaml's GC may move/free it.

**Fix**: each callback registration allocates a `CallbackBox` on the C
heap, stores the closure value in it, and registers `&box->closure` as a
generational global root. The trampoline reads through the root, which
GC keeps stable.

The root is registered only while `solve` runs: `Hexaly.solve` pins every
callback of the optimizer before calling into Hexaly and unpins them
afterwards. A permanent root would keep the closure alive, and a closure
that captures its optimizer (the common case) would then keep the
optimizer alive forever. Outside `solve`, the optimizer record owns its
callback records and each callback record holds its optimizer; that
cycle is plain OCaml data, so the GC collects it.

The box finalizer only unregisters the root (if pinned) and frees the box.
It must not call into the optimizer: when an optimizer and its callbacks
become unreachable together, finalizers run in no particular order, so
the optimizer may already be freed. `hxs_optimizer_free` drops the
shim-side callbacks itself.

### Pitfall 4: user-callback exceptions

If the user's OCaml closure raises, the exception must NOT propagate into
Hexaly's C++, because that would unwind across the ABI boundary and corrupt
state.

**Fix**: the trampoline uses `caml_callback_exn` (the non-throwing
variant) and checks `Is_exception_result`. On exception, we print a
warning to stderr and return cleanly to Hexaly. Document this clearly so
users wrap their callbacks in `try ... with _ -> ()` if they care.

## 5. Batched create_expression

Building a model with N expression nodes through a naive binding does N
FFI crossings. At 100 ns each (a generous ctypes estimate), 1M nodes is
100 ms of pure FFI overhead.

We batch: `hxs_model_create_expression` takes an array of operand
handles + an array of int leaf constants + an array of float leaf
constants, all in one call. One OCaml→C transition builds one expression
node regardless of its arity.

The OCaml side helper `mkn m op xs` does:

```ocaml
let mkn m op xs =
  let arr = Array.of_list (List.map (fun e -> e._eh) xs) in
  wrap m (m_create_expression m._mh (Op.to_int op) arr empty_ints empty_floats)
```

The C stub handles up to 64 operands on the stack, mallocs for larger.

Benchmark: 1M expression nodes in 187 ms = ~190 ns/node, including the
OCaml-side record allocation, list-to-array conversion, and FFI. Drops
to ~50 ns/node if you use `create_expression ~operands:[|...|] ()`
directly with a pre-built array.

## 6. Mock backend semantics

The mock is a binding test fixture, not a real solver. It implements:

- **Faithful**: bool/int decisions, every arithmetic/comparison/boolean
  op, brute-force search with constraint filtering, close-state
  enforcement, typed error propagation.
- **Approximated**: interval (always returns a degenerate [lo, lo)
  point), list/set (always returns identity [0..n-1]). The brute force
  can't enumerate permutations / interval combinations efficiently.
- **Unmodeled**: math functions (sqrt, log, etc.) return 0 to avoid
  recursion. Tests for these skip on mock.

The mock fires `Optimization_started` / `Optimization_ended` callbacks
around its `solve()` so callback tests can verify firing on both
backends.

## 7. Cross-platform build (no bash required)

OCaml runs on Linux, macOS, Windows, and the BSDs. So should the binding.
But many bindings end up with `configure.sh` calling `uname`, `pkg-config`,
shell glob expansion, none of which work on Windows without WSL/Cygwin.

This binding uses **`dune-configurator`** instead. The configurator is
plain OCaml (`src/config/discover.ml`). It:

1. Reads `HEXALY_BACKEND` / `HEXALY_HOME` env vars.
2. If unset, scans common install paths
   (`/opt/hexaly_*`, `/Library/hexaly_*`, `$HOME/hexaly_*`,
   `C:/hexaly_*`, `$ProgramFiles/hexaly_*`).
3. Discovers the exact library soname (`libhexaly145.dylib` → `-lhexaly145`)
   by listing the `bin/` directory instead of hardcoding a version.
4. Uses `Configurator.V1.ocaml_config_var "system"` for platform-conditional
   flags (`-Wl,-rpath,` on macOS vs `-Wl,-rpath=` on Linux; `-lc++` on
   macOS vs `-lstdc++` on Linux; nothing on Windows).
5. Emits the same `c_flags.sexp` / `cxx_flags.sexp` / `c_library_flags.sexp`
   / `hexaly_shim.cpp` files the bash script did.

The dune rule that runs it is one line:
```
(rule (targets ...) (deps ...) (action (run %{dep:config/discover.exe})))
```

Result: one build pipeline with no shell dependency. The configurator
handles Windows paths and library names, but the Windows build has not
been tested.

## 8. What's not bound (and why)

- **`HxExternalFunction`**: registering OCaml as a black-box evaluator
  inside a Hexaly expression. Same lock-dance pattern as callbacks but
  stateful (Hexaly may call the function thousands of times per
  iteration). Needs more careful perf engineering; deferred.
- **`lambdaFunction` / `range`**: Hexaly's array-comprehension idiom
  used in their canonical TSP. Compiles to closures registered with
  Hexaly. Same complexity as external functions. Defer.
- **`load_environment` round-trip with `save_environment`**: Hexaly 14.5
  saves a `.hxm` Modeler script but `loadEnvironment` doesn't accept
  it back. The saved file IS loadable by the Hexaly CLI, so model
  export still works for sharing/debugging.

## 9. Performance summary

On a 2026 Apple Silicon Mac with Hexaly 14.5:

| Operation                          | Time     | Per-unit       |
| ---------------------------------- | -------- | -------------- |
| Create 1000 int vars               | < 1 ms   | < 1 µs / var   |
| Build 1M expression nodes          | 187 ms   | 190 ns / node  |
| `close` (Hexaly model compilation) | 541 ms   | one-shot       |
| Solve (1 sec time limit)           | 39 ms    | one-shot       |

The 190 ns/node figure is the binding-overhead ceiling. For comparison,
ctypes is typically 1–3 µs/call; raw cpython is ~600 ns/call.

The Hexaly C++ engine's perf is invariant to which language binding
you use: every binding ends up in the same `libhexaly` solve loop.
